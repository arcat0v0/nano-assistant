# Runtime and tool execution

`na chat` builds an Agent for a one-shot prompt; the interactive CLI/TUI delays construction until the first prompt or model switch so `/model add` remains available without a configured default-model key. Rig 0.42 owns provider message conversion, streaming events, tool-call IDs/results, and the multi-turn model/tool exchange; its model-bound agent can be replaced between turns. The application keeps only session concerns: the system prompt, Markdown memory, complete-turn history trimming, dynamic tool registration, and output rendering. `behavior.max_iterations` defaults to 50 and limits Rig turns; `memory.max_messages` limits retained history without separating a tool result from its originating call.

Model selection resolves `[models].default` and local named profiles before constructing the Rig model handle; legacy `[provider]` is the implicit `default` profile. CLI `--profile` and `--model` override only the current process. In an interactive terminal, `/` opens a keyboard-selectable command palette (arrows select, Right completes), and `/model` opens a second menu for choosing a profile or adding a provider; piped `/model` still lists profiles. Direct `/model <profile>` constructs the replacement model before swapping Rig's agent between turns, reusing the live tool server, policy hook, MCP connections, Markdown memory, system prompt state, and complete-turn history; `/model <profile> --save` also persists the default profile. A failed switch leaves the active agent unchanged. Provider-specific API URLs and credentials are isolated across profiles, and an explicitly configured `api_key_env` must be present.

`/model add [provider]` selects a model from the built-in provider's live catalog and saves a local profile, optionally as the default. It reads the API key from the selected environment variable and stores only that variable's name. `na model discover <provider>` queries the same catalog without modifying config. DeepSeek, Kimi, and MiMo use their own model endpoints; Qwen's catalog is distinct from its chat endpoint and pages through models filtered for the vendor and function calling. If the default GLM model endpoint returns 404/405, the client extracts text-model IDs from Z.AI's published pricing page instead; these do not establish account entitlement. MiMo uses the `api-key` header for chat and catalog requests; GLM uses the official Bearer API key.

Normal interactive and one-shot startup creates a missing configuration directory and file using the binary's first-run defaults (DeepSeek / `deepseek-flash`), before resolving credentials or constructing an Agent. Existing files are not overwritten, and creation failures stop startup. `--config-path` selects the file to initialize; `--help` and `--version` do not initialize anything. Configuration is edited directly rather than through the removed `--config` editor entry point.

Compatibility: tool execution requires a model with native tool/function calling; the XML fallback is removed. Deploy the native-tool-aware `nana-hub` alongside clients using `free/*`: an older text-only Hub cannot handle native tool-call and result history.

Builtin tools are registered in Rig's live tool server. Skill, knowledge, and MCP dynamic tools use distinct provider-compatible function names: `skill__<encoded-skill>__<encoded-tool>`, `knowledge__<encoded-source>__search`, and `mcp__<encoded-server>__<encoded-tool>`. Non-alphanumeric UTF-8 bytes in each component are escaped as `_xx` (for example, `arch-wiki` becomes `arch_2dwiki`); calls still dispatch to their original skill, source, or MCP tool. MCP servers retain the configured stdio, HTTP, or SSE transport; with deferred loading, `tool_search` discovers the encoded names and activates them in the same registry for the next model request. Installing a skill triggers a rescan; editing the active `config.toml` through `file_edit` or `file_write` reloads newly configured MCP servers. The policy hook checks all tool calls before execution, including activated tools. `direct`, `confirm`, and `whitelist` preserve their configured meanings; a denied tool call has no tool side effect and is visible to the model.

Tool hooks render numbered start/result lines on stderr in streamed and nonstreamed modes; the genuine built-in `ask` instead owns its interaction card and completed summary. Argument previews escape terminal controls. Streaming uses an acknowledged output boundary before hooks display tools or enter human interaction, so loading text and final Markdown redraw do not overwrite cards or earlier conversation. Assistant text stays on stdout. Auto policy separates risk from authorization: prohibited/outside-scope actions are denied first; high risk or unclear authorization requires current human confirmation; otherwise unknown risk or any reported missing evidence returns to the main model for investigation without execution or an approval prompt. Low/medium risk with clear scope and no missing evidence may execute. Identical rejected actions are cached for the current user request and clarification revision; investigation requests are not, so the same action can be reviewed again after facts are gathered. Confirmation defaults to rejection and displays the actual resolved action; details retain non-command parameters such as PTY scripted responses. Whitelist matching evaluates the original shell command string.

`file_edit` requires exactly one nonempty `old_string` match. A missing or repeated match produces a structured tool error and leaves the file unchanged, so the model can revise its request. Builtin skill source files cannot be edited or overwritten. Shell and PTY execution remain local.

The built-in `ask` gathers 1–4 related questions, with 2–6 options or a free-text answer. Recommendations set focus only. Cards support arrows, Enter, multi-select Space, custom text and bracketed paste, Shift-Tab backtracking, and resize/scrolling without changing answers. Confirmation uses the same card: `d` expands full details, `y` allows only this action, and Enter defaults to refusal. Both use numbered/plain confirmation text when stdin/stderr are not suitable TTYs or TERM is dumb; empty input is never implicit approval.

Successful real answers enter a separate token-tagged clarification section for this turn, containing only selected options and custom text. Model questions explain a choice but cannot grant authorization; unselected options, fabricated tool results and restored session history cannot populate that section. Answers are not execution approvals. Ask cancellation/EOF/unavailability blocks subsequent tools until the next genuine user turn. Eight successful batches and 64 KiB of trusted clarification JSON are the per-turn limits; accepted clarification revises the denial-cache key without clearing prior execution/refusal history.

For `free/<slug>`, the Hub transport sends `<slug>` to `/v1/chat/completions` with the existing Ed25519 request signature and exact signed JSON body. Hub routes native tool calls but does not execute them; subsequent requests include the corresponding tool-call IDs and local results. The free route currently accepts text only and rejects image input. Use an isolated Hub, database, Redis, and mock upstream when validating this flow; production credentials are not required.


## Safety review boundaries

The reviewer uses the strict categorical protocol documented in [security-review.md](security-review.md). Task authorization comes from the unchanged genuine user-request section and this turn's actual selected clarification answers, never actor-written fields or history. Prepared-mutation filesystem facts remain in their separate runtime-evidence section. Recent-action history is limited to 20 entries and 32 KiB, with truncation indicated; it excludes tool stdout/stderr and persistent memory.

The isolated reviewer has only four read-only tools: bounded path metadata/list/text/digest, ZIP/TAR/TAR.GZ metadata and member digests without extraction, Docker/Podman local inspection, and fixed local systemd properties. It does not use the main tool server, arbitrary shell, MCP or network endpoints. Probe results preserve provenance, connection scope, incompleteness and errors; common credential paths/content are excluded or redacted, not claimed to form an exhaustive secret sandbox. Linux-only system probes explicitly report unavailable elsewhere. Docker selection honors the process context/host configuration and freezes a verified local Unix socket; Podman stays current-user local, with no cross-runtime fallback.

Each review permits at most 120 model requests, 160 evidence calls and 1.25 MiB (1280 KiB) of evidence JSON, with 16 KiB per result and an overall deadline of 60 model timeouts. These whole-review budgets are twenty times their initial limits; individual model/probe timeouts, filesystem/archive bounds and safety policy are unchanged. For example, a configured 30-second model timeout gives an overall maximum of 30 minutes, not an expected duration. Budgets bound runaway loops and context/cost growth, not the number of legitimate resources a normal action should inspect. Malformed final responses still have at most three protocol attempts. A first final verdict missing observable facts gets one bounded supplementation opportunity before returning to the main model. Reused successful requests consume call and output budgets without rereading. An automatic Allow revalidates collected path snapshots; failures/changes become missing facts and require investigation, not approval. The reviewer never changes the frozen action. Infrastructure/protocol failures, including exhausted review budgets without a valid final verdict, retain fail-closed independent confirmation; a valid unknown-risk or missing-evidence verdict instead hands investigation back to the main model.

Investigation blocks the proposed execution and returns tool failure feedback beginning `Safety review requires investigation:`, with the reason, missing facts and instructions to gather observable evidence. History records `investigation_required`. The main model must investigate through normally authorized tools, then resubmit the original action for review with the resulting evidence; it must not retry unchanged or bypass review. Real user choices about scope or data policy belong in Ask, not invented runtime evidence. Only facts needed to judge this current action belong in `missing_evidence`; noncritical unknowns about unrelated later steps belong in `reason` and must not obstruct a safe read-only diagnostic. Even a low-risk verdict with a nonempty `missing_evidence` list requires investigation under the deterministic gate.

The hook authorizes ordinary tools. Registered builtin file mutations and expanded skill tools authorize inside their executor so the reviewed operation is the one executed. Dynamic replacements revoke builtin prepared-executor exemptions. File snapshots detect content, identity, parent-path, and symlink changes; creation uses exclusive creation. These checks are not an OS sandbox or a transactional filesystem. External-process races after the last check and partial writes on I/O failure remain possible.
