# Runtime and tool execution

`na chat` builds an Agent for a one-shot prompt; the interactive CLI/TUI delays construction until the first prompt or model switch so `/model add` remains available without a configured default-model key. Rig 0.42 owns provider message conversion, streaming events, tool-call IDs/results, and the multi-turn model/tool exchange; its model-bound agent can be replaced between turns. The application keeps only session concerns: the system prompt, Markdown memory, complete-turn history trimming, dynamic tool registration, and output rendering. `behavior.max_iterations` limits Rig turns; `memory.max_messages` limits retained history without separating a tool result from its originating call.

Model selection resolves `[models].default` and local named profiles before constructing the Rig model handle; legacy `[provider]` is the implicit `default` profile. CLI `--profile` and `--model` override only the current process. In an interactive terminal, `/` opens a keyboard-selectable command palette (arrows select, Right completes), and `/model` opens a second menu for choosing a profile or adding a provider; piped `/model` still lists profiles. Direct `/model <profile>` constructs the replacement model before swapping Rig's agent between turns, reusing the live tool server, policy hook, MCP connections, Markdown memory, system prompt state, and complete-turn history; `/model <profile> --save` also persists the default profile. A failed switch leaves the active agent unchanged. Provider-specific API URLs and credentials are isolated across profiles, and an explicitly configured `api_key_env` must be present.

`/model add [provider]` selects a model from the built-in provider's live catalog and saves a local profile, optionally as the default. It reads the API key from the selected environment variable and stores only that variable's name. `na model discover <provider>` queries the same catalog without modifying config. DeepSeek, Kimi, and MiMo use their own model endpoints; Qwen's catalog is distinct from its chat endpoint and pages through models filtered for the vendor and function calling. If the default GLM model endpoint returns 404/405, the client extracts text-model IDs from Z.AI's published pricing page instead; these do not establish account entitlement. MiMo uses the `api-key` header for chat and catalog requests; GLM uses the official Bearer API key.

Normal interactive and one-shot startup creates a missing configuration directory and file using the binary's first-run defaults (DeepSeek / `deepseek-flash`), before resolving credentials or constructing an Agent. Existing files are not overwritten, and creation failures stop startup. `--config-path` selects the file to initialize; `--help` and `--version` do not initialize anything. Configuration is edited directly rather than through the removed `--config` editor entry point.

Compatibility: tool execution requires a model with native tool/function calling; the XML fallback is removed. Deploy the native-tool-aware `nana-hub` alongside clients using `free/*`: an older text-only Hub cannot handle native tool-call and result history.

Builtin tools are registered in Rig's live tool server. Skill, knowledge, and MCP dynamic tools use distinct provider-compatible function names: `skill__<encoded-skill>__<encoded-tool>`, `knowledge__<encoded-source>__search`, and `mcp__<encoded-server>__<encoded-tool>`. Non-alphanumeric UTF-8 bytes in each component are escaped as `_xx` (for example, `arch-wiki` becomes `arch_2dwiki`); calls still dispatch to their original skill, source, or MCP tool. MCP servers retain the configured stdio, HTTP, or SSE transport; with deferred loading, `tool_search` discovers the encoded names and activates them in the same registry for the next model request. Installing a skill triggers a rescan; editing the active `config.toml` through `file_edit` or `file_write` reloads newly configured MCP servers. The policy hook checks all tool calls before execution, including activated tools. `direct`, `confirm`, and `whitelist` preserve their configured meanings; a denied tool call has no tool side effect and is visible to the model.

In streamed mode, completed Rig tool-call and tool-result events render brief progress on stderr, while assistant text stays on stdout. Confirmation prompts include the actual tool name and arguments/path, including skill and MCP tools. Whitelist matching still evaluates only the original shell command string.

`file_edit` requires exactly one nonempty `old_string` match. A missing or repeated match produces a structured tool error and leaves the file unchanged, so the model can revise its request. Builtin skill source files cannot be edited or overwritten. Shell and PTY execution remain local.

For `free/<slug>`, the Hub transport sends `<slug>` to `/v1/chat/completions` with the existing Ed25519 request signature and exact signed JSON body. Hub routes native tool calls but does not execute them; subsequent requests include the corresponding tool-call IDs and local results. The free route currently accepts text only and rejects image input. Use an isolated Hub, database, Redis, and mock upstream when validating this flow; production credentials are not required.
